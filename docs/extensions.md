# The `x-mock-*` extensions

OpenAPI describes shape and constraints. What it cannot say is "this is a
person's name" or "seed forty of these", and without that a spec-derived mock
produces a list of users called `string`, `string`, `string` — technically
valid, useless to build a screen against.

Four extensions cover that gap. They are vendor extensions, so a spec carrying
them stays valid and every other tool ignores them.

## `x-mock-count`

How many items to seed. Goes on the **array schema**, not on the envelope
around it.

```yaml
data:
  type: array
  x-mock-count: 40
  items: { $ref: '#/components/schemas/Book' }
```

Putting it on the response object is the easy mistake — and this tool made it
first: reading the count off the response schema silently ignored every
`x-mock-count` in a paginated spec, which is most of them.

Default: 5.

## `x-mock-faker`

A dotted path into [faker](https://fakerjs.dev). The value is generated by
calling it.

```yaml
title: { type: string, x-mock-faker: commerce.productName }
name: { type: string, x-mock-faker: person.fullName }
city: { type: string, x-mock-faker: location.city }
```

An unknown path produces a warning and falls back to schema-driven generation.
A typo in a vendor extension should not stop a mock server from starting.

## `x-mock-value`

A fixed value, used verbatim. For the fields a client keys off:

```yaml
status: { type: string, x-mock-value: active }
featureFlags:
  type: object
  x-mock-value: { newCheckout: true, darkMode: false }
```

## `x-mock-relation`

Draw the value from the ids of another seeded collection, so a foreign key
points at something that exists:

```yaml
authorId: { type: integer, x-mock-relation: authors }
```

Collections are seeded in dependency order, so `authors` exists before the
books that reference it regardless of the order the paths appear in the spec. A
cycle — two collections referencing each other — falls back to declaration
order with a warning, and one of them gets generated ids.

Pointing at a collection that was never seeded produces a warning and a
generated value, not a crash.

## Where they are read

| extension         | read from                               |
| ----------------- | --------------------------------------- |
| `x-mock-count`    | the array schema of a list response     |
| `x-mock-faker`    | any schema                              |
| `x-mock-value`    | any schema                              |
| `x-mock-relation` | any schema, resolved against seeded ids |

## What the tool does without them

Formats do most of the work: `date-time`, `date`, `email`, `uuid`, `uri`,
`hostname`, `ipv4`, `password` and `byte` all generate something that looks
right. `enum` picks from the declared values. `minimum`, `maximum`,
`minLength` and `maxLength` are respected.

`pattern` is **not** honoured — matching an arbitrary regex needs a
regex-to-string engine — and the tool warns when it meets one rather than
quietly generating a value that fails the spec's own constraint.
